# Automatic read-only offline room viewing — implementation plan

Status: **approved product scope; implementation and tests not started**. This plan is for the `offline-research` change stack based on `main`. It does not describe current behavior. See [option research and sources](offline-options.md), [current architecture](../ARCHITECTURE.md), [remembered room access and installation](../docs/home-screen-installation.md), and [browser-test harness](../docs/browser-testing.md). Any frontend/database architecture change outside the small offline-only browser view must be raised with the owner first.

## Agreed behavior and limits

- A successful **online, room-authorized visit** automatically saves **all lists and their items for that room** to the *same browser installation*, quietly. Room authorization, not admin login or mere possession of a room slug, determines what can be downloaded. No separate user accounts exist: “your lists” means lists in the room for which the browser has a valid room grant. Never fetch all rooms or public links as a side effect.
- The installed app's `/room/{slug}` entry shows the saved room and lets the user open its lists **read-only** after connectivity fails. The saved view includes the list names, items, done state, quantity, and existing item details/tags needed to understand the list; its presentation can be simpler than the NiceGUI editor. No edits, checkboxes that change state, buttons with writes, queues, or claim that another device has seen these items. Show **“Offline · read only”** and an accurate **“Last saved”** timestamp; do not imply the list is current.
- Only **one room snapshot per browser origin** in v1. If someone legitimately opens another room, replace the old snapshot only after the new room snapshot has been fully validated and stored; never combine rooms. This is a storage boundary, **not** a change to existing online room navigation, room links or permissions. Shared `/share/{token}` links are online-only for v1, even if they point into the cached room.
- Re-save automatically in the background of an **open app**: after an authorized room visit, on return to a visible authorized room/private-list page, on reconnect and after confirmed writes from those pages. Coalesce rapid events; do not fetch on every keystroke, show routine success toasts, or promise OS background downloads while the app is closed. A change made by another person may be absent until the next successful refresh; the timestamp makes this visible. When refresh fails, keep a valid previous snapshot and its **previous** timestamp, with a small non-toast warning where users might otherwise assume a newer copy exists. A fresh device or failed first save must say no offline copy is ready.
- Revocation/deletion cannot be detected by a device with no network; the owner accepts the old copy remaining viewable until it reconnects. When a successful server check returns **definitive** invalid/removed-room status, clear that room's snapshot and show sign-in/unavailable, never serve it as current. Treat network/temporary database failures differently: preserve the old snapshot, show that verification/update failed, do not mislabel it as revoked or newly saved. Offline storage is device-local and may be evicted/cleared; do not promise availability without a verified successful save.
- No “Remove offline copy” button in v1: automatic saving would immediately repopulate it. An opt-out control, if ever desired, must both clear and stop automatic saving; [track separately](backlog.md#ui-and-pwa).

**Practical assumption for v1:** background means while a page is open, not after closing the app. No offline boot on a device that has not completed at least one online authorized save. Deep `/list/{slug}` bookmarks and `/share/{token}` are not promised offline entry points; room home-screen launch **and** existing `/` root-launch icons should reach the one saved room. If real-device behavior blocks the old-icon path, report it before changing this promise. An online NiceGUI list already open when signal drops may lose its live controls: provide a plain “View saved lists” path that does not pretend they still work. If actual device testing challenges these assumptions, stop and ask before broadening scope.

## Design seams to implement (small, independently testable chunks)

### 1. One authorized, bounded room snapshot endpoint (server)

- Add a **GET** endpoint dedicated to the offline room snapshot; keep the existing NiceGUI room/list routes and SQLite. Reuse the room-token validation used for private pages. Accept the existing secure HttpOnly cookie on HTTPS; for existing HTTP/cookie-failure localStorage fallback, send its *already remembered* token in a same-origin custom request header, **never** URL/query/response/IndexedDB/service-worker cache. Do not create a second offline permission mechanism. Reject admin-only sessions, missing/wrong-room/expired tokens, deleted rooms, and public share tokens. Origin when present and Fetch Metadata when present must be same-origin; use no credentialed CORS or wildcard. A header alone is not proof of access: every request still validates the current token against SQLite.
- Return just the authorized room's public routing slug and display name plus its lists/items (including empty lists and done items) in a small versioned JSON shape. No passwords, access tokens, share tokens, invitation data, other rooms, or admin metadata; no personally identifying browser storage keys in the payload. Use `Cache-Control: no-store` (and suitable referrer protections); never store the JSON in the HTTP Cache API. Put authorization and the room/list/item read in one deliberately scoped database read lock/consistent read so a concurrent delete or password change cannot leave a cross-room or partial snapshot. If a bounded-size/count check is needed, reject the **entire** new snapshot with an explicit error rather than silently dropping lists/items. Document the actual bound before implementation.
- Return explicit responses for 401/403 invalid authorization and 503/transient database failure. A deleted room may invalidate its token, so **do not require a distinguishable 404** if that would expose room existence; both revoked and deleted grants should cause the client to discard its matching old copy on a reachable definitive denial. Do not turn a database error into “empty room.” Test a token revoked *between* initial page render and subsequent fetch, not only a direct unauthenticated request. Keep this a read API, without migrations or mutation endpoints.

### 2. Save atomically on the browser (client)

- On a validated room page **after** browser token/cookie migration and authorization, trigger a same-origin fetch for the one room. Also trigger from a **room-authorized private list page** after confirmed writes, and on room/private-list visibility/online return with bounded backoff and debounce (verify the server response rather than trusting `navigator.onLine`). Do not start from root/admin/password prompts/public pages. Reuse one small browser module; avoid duplicating JS across NiceGUI pages or refetching on every render. A successful write can trigger one coalesced room snapshot refresh; it must still pass current authorization before replacing the saved copy.
- Write the complete validated snapshot and server-success save time in **one IndexedDB transaction**, with schema versioning, one fixed record/key, and replacement semantics. The transaction must preserve the last good copy on HTTP, JSON/schema, quota, aborted transaction or storage error. An empty authorized room **replaces** old content (not “skip because there are zero lists”). When replacing room A with room B, never expose a mixed A/B snapshot. Never store a room password, bearer token or share-token URL in the offline record. Distinguish *no saved copy*, *old copy after failed update*, *saved at time T*.
- On definitive authorization failure for the cached room after a reachable server response, erase/disable that snapshot; on transient failure do not erase. Clear a deleted room on reconnection too. The browser can be offline during revocation; do not claim instant deletion. Do not add an always-on background sync feature or ask for persistent-storage permissions without evidence it helps the MVP.

### 3. Minimal independent offline shell + navigation fallback

- Add a small versioned, **generic** HTML/CSS/JS shell as static files. Service worker precaches only this generic shell/assets and explicitly controls its cache version on update; **never** caches NiceGUI HTML, API JSON, authenticated room pages, `/share/`, or a token-bearing request. Network-first navigation fallback serves the shell only for the selected `/room/{slug}` route (and `/` for an older root-launch icon); only on genuine network failure/timeout, **not** on HTTP unauthorized, missing-room or server-error responses. Routes outside the allowlist are not an accidental portal to a saved room. The shell reads IndexedDB and verifies that the requested slug is the saved room before displaying private content. Root fallback can read the one saved room without needing to cache any secret or last-room cookie.
- Use the same safe local shell when an already-open NiceGUI room/list page loses connectivity; offer a passive read-only link, not duplicated working edit controls. If someone opens the shell **while the server is reachable**, attempt a fresh authorized check **before** showing stored private content, so a revoked copy is cleared rather than displayed online. Only use the stored copy without this check on actual connection failure; treat temporary server errors as stale/unverified, not as successful access. Render list/item text as text (not HTML); keep all list contents inside the browser's data store, not in the service-worker HTTP cache. Make checked-off items legible (including any currently-hidden items; this plan is based on `main` and should recheck display rules if other feature branches are integrated). Show a clear generic *no copy prepared* state and a *stale/last saved* state. Online authorized page behavior, manifest scope/identity/start URLs, login flow, and sharing routes must continue to work unchanged.
- Offline shell should not trigger an endless navigation/reload loop; online again, reopening the room should return to the ordinary NiceGUI editor and refresh the copy. The service worker may be activated after first registration/reload: do not display “available offline” until installation, control, and IndexedDB commit are demonstrably ready. Avoid aggressive `skipWaiting`/cache cleanup that could break an older open tab during an update; test both old and new installed icons.

### 4. Current behavior references and recovery

- After a verified implementation, update [architecture](../ARCHITECTURE.md), [installation/access guide](../docs/home-screen-installation.md), [browser testing](../docs/browser-testing.md), and [backlog](backlog.md) with **actual** behavior and outstanding device checks. Explain privacy on a shared/lost phone, browser storage clearing/eviction, one-room limit, stale timestamp, reconnect/revocation, and how to confirm a room is available before entering a shop. Do not describe planned support as deployed. No changes to SQLite schema, server hosting, or NiceGUI online editing unless a tested prerequisite forces a separate decision.

## Verification plan and acceptance gates

Use temporary databases, distinct browser contexts, and disposable rooms only; never inspect/download production lists for testing. Tests for each chunk before expanding scope:

| Layer | Cases to prove | Pass condition |
| --- | --- | --- |
| **Endpoint unit/integration** (`tests/`) | Valid cookie, HTTP fallback header, no token, wrong-room, admin-only, public share token, revoked/expired token, deleted room, room with zero lists, empty list, done items and item details, encoded names, concurrent delete/reset at read boundary, database error, oversized payload. Test another browser context cannot fetch cached room's JSON. | Exactly one room's current data, no secret fields, no-store headers, fail closed on auth; 503 is not a success/empty snapshot; consistent read under concurrent writes. |
| **Client/SW unit or browser checks** | Precache only generic files, stable version update, routing allowlist including root and room slug, network-only share/admin/invitation paths, response-status distinction, no HTML/JSON/private token in Cache API; IndexedDB full commit, empty replacement, room replacement, schema mismatch, quota/abort preserves previous copy; render untrusted names as text. | Private cache contains only the selected room record; never mix rooms or show successful-save time on failure; no edit events from shell. |
| **Real browser (Chromium + Firefox, `browser_tests/`)** | Online login and wait explicitly for SW control + saved snapshot; go offline (Playwright `context.set_offline(True)`), cold reload `/room/{slug}` and older `/`, open every saved list including never-visited ones; contrast fresh context/no copy, wrong room, public link/admin route, and list-only session; test broken connection while normal page is open; restore network, edit from second context, focus/revisit and verify new snapshot and time; edit from an authorized private list page then go offline without returning to the room. Simulate dropped endpoint response, 503, auth revocation, room/list/item deletion, room replacement, empty room, rapid concurrent refresh, injected IndexedDB failure, reinstall/worker update, old icon. | Offline view works only after full authorized preparation; updates and removals appear after successful reconnect, no bogus success/erase on transient failure, normal online editing/launch and sharing remain unchanged. Avoid sleeps as readiness proof. |
| **Security/HTTPS smoke** | Disposable HTTPS server and cookie-backed installed-like browser context; HTTP/localStorage fallback separately. Try cross-room/cross-origin requests and inspect actual Cache API + IndexedDB + network requests (including query strings) for tokens, unexpected HTML, other room contents. Simulate password revocation while one browser remains offline, then reconnect. | Credential checks still gate every online read; old offline data can be read while offline (explicitly accepted), then removed on definitive revoked/deleted status. | **Manual real devices** | iPhone Safari **installed app** and Android Chrome installed app/shortcut: fresh install with/without prior sign-in, open room online and wait for save, enter shop-like airplane mode, force-close/relaunch, choose every list, restore signal, test changed/deleted room/password from second device, background/foreground, storage eviction/clearing, old root icon, update with previous worker. Record OS/browser versions and observations. | No promise of offline launch, persistence, or silent background refresh on a platform until this exact scenario has been demonstrated; record failures as pending, do not infer from desktop Playwright. |

Run focused tests at each chunk, then the repository's required Python checks **if Python files changed** (`uv run ruff format .`, `uv run ruff check --fix .`, `uv run pytest -q`, `uv run ruff format --check .`, `uv run ruff check .`). Run the opt-in real-browser suite via [its documented command](../docs/browser-testing.md#run) (`uv run pytest browser_tests -q -n 0`). Inspect diffs and cache contents and test the existing room access, sharing, installation, and deletion regressions. Report manual-device checks separately as verified or outstanding; automated desktop tests are not a substitute. This plan itself is not evidence any test has run.

## Deferred outside this first version

- Offline editing and synchronization (operation queue, conflict rules, stable item IDs, writes while revoked); see [research](offline-options.md) and [backlog](backlog.md#ui-and-pwa).
- Opt-in storage of individual public share links, with separate token-rotation/privacy design; an offline shared link must never silently grant room access. See [public sharing](../docs/public-sharing.md).
- An offline opt-out/privacy switch that **also prevents automatic re-download**; a one-shot “remove offline copy” is not useful with automatic saving. Multi-room offline switching is **not** a product goal; do not build it as a deferred feature.
- Closed-app/guaranteed background downloads, offline `/list/{slug}` deep links and exact parity with the NiceGUI editor; reconsider only if real usage makes them necessary.
