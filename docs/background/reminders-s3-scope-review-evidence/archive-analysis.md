## Key code and architecture

- The archived scheduler runs `_tick()` on an interval, scans `(installation_id, room_id)` scopes in batches, calls recovery/pruning and then `generation.evaluate_enrollment_locked`; a bounded recurring job is a different product from “show it only after the user opens the app” (`scheduler.py@22ee` lines 63–82, 84–162, 178–185).
- The archived strip is foreground/online-gated (`ReminderStrip.svelte@ef495` lines 13–29, 52–91), but its `StripState` still claims server-generated S3 events. It is not a scheduler-free daily-only implementation.
- The inbox action API scopes lookup by both installation and room, checks authorization before replay, uses a revision and personal op ID, and never edits due items (`reminder_inbox.py@8cb` lines 255–334; `test_api_reminder_occurrence_actions.py@8cb` lines 24–75, 78–131). Those are good invariants; the endpoint is coupled to S3 event and receipt rows.
- The current API has device settings and policy routes but no inbox router (`src/api/__init__.py@9e` lines 26–40); the current schema stops at migration 18 (`src/database_setup.py@9e` lines 1132–1144). This is the concrete compatibility boundary: a code transplant needs S3’s event schema and route registration, not just a new button.
- S3’s restore guard does fail closed when paused, missing, malformed or contended; it is designed to serialize the scheduler with an external restore-state writer (`runtime_guard.py@c5` lines 1–5, 21–85). d625 carries this protection only through the scheduler’s database work (`CURRENT.md` lines 23–33). It is a useful future safety pattern, not a reason to adopt background execution in the small release.

## Recommendation and residual questions

1. **Proposed smallest useful scope:** when a room’s connected page becomes visible at/after that device’s configured local summary time, show one concise summary of the server’s *current* due items. Store a durable unique `(installation, room, local day)` claim/receipt and acknowledgement, atomically, under the already-validated room and device cookies. Other tabs/devices/rooms must not consume or see each other’s receipt. Do not backfill missed days; do not run while closed/offline; do not call this a phone notification.
2. Build the claim from current due facts, not copied historical item names. Keep active-grant and room authorization checks on every read/action; revoke on sign-out/password change as existing enrollment rules require. Use same-origin JSON writes and idempotent retries; after an ambiguous replay, refresh authoritative state instead of treating an old receipt as current.
3. Do not include custom rule scheduling, summary snooze, overdue repeats/cooldown, multiple reminder histories, manual “remind now”, push, or S4/S5 fallback/accounting. The existing due bell already supplies all-item discovery; this release’s only incremental benefit is a once-a-day in-app prompt when the user next returns.
4. **Before settings are exposed**, perform S3 brief’s P2 work: enable entry points through the single flag; compact accessible per-item action; plain “off on this device” flow and retry only on real load failure; plain-language labels; phone-width/light-dark browser checks; unskip the private-reminders and policy-editor tests (`reminders-s3.md` lines 28–47; P2 record lines 35–47). P2’s settings tests are deliberately paused, not passing.
5. **One optional historical test set only if code-extraction is still seriously considered:** on a disposable exact `acb88235` snapshot, `uv run pytest -q tests/test_api_reminder_inbox.py tests/test_api_reminder_occurrence_actions.py tests/test_reminder_receipts_migration.py`. Fixture safety inspected: conftest uses `DB_PATH=:memory:` and a test-only password; migration coverage uses `tmp_path` SQLite; FastAPI `TestClient` is in-process. This set has no provider/external-service sends, but tests the full archived schema, so even green results would not prove a minimal migration fits baseline v18. It was not run by this scout and is not recommended before scope selection; the parent’s 150-test run already covered the broader combined runtime slice.
6. **Recovery caveat:** a backup restore could roll the daily acknowledgement back and cause a second in-app prompt that day. Because the proposed path has no background or external send, that is a low-impact but real case; either explicitly allow/retest the behavior after restore or have the approved implementation define a restore boundary. Do not claim archived d625 fully solves it: that guard was reviewed only as a scheduler prerequisite and does not guard final I/O or this proposed API.
