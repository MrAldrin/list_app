## Key Code

- **The due center is already a complete passive overview, not a reminder delivery feature.** It includes every unchecked dated item from overdue through later, while its badge only counts overdue/today/tomorrow; opening the panel does not clear it. Rows navigate to the item. Confirmed timed items use the stored instant for overdue status; unconfirmed edits use the date without inventing an instant (`due-reminders.ts:70–103, 110–150`; `DueCenter.svelte:44–80, 83–162`). The item editor already saves a shared due time and IANA zone; clearing date clears time/zone (`ItemDialog.svelte:74–102, 138–207`). Current docs explicitly say no reminder toast and no phone notification (`docs/due-date-reminders.md:3–22`).
- **The actual new effect in the parent’s foreground-summary candidate is presentation/handled state, not new due facts.** One compact grouped summary on the first connected, visible room visit at/after that device’s configured local summary time could make an otherwise passive due count harder to miss, and an acknowledgement could avoid repeating it that day. However, the bell already shows the same overdue/today/tomorrow items and a badge; this is meaningfully different only if it stays a brief nudge with a persistent per-room/per-device/local-day handled record, not a second full due list. For five users, the gain is modest. Deferral remains reasonable if users do not want a daily prompt.
- A simple candidate should be **foreground-only**: do not promise a prompt while the app is closed, a tab is suspended, or the device is offline. Check on connected open/visible return and after reconnect; no old-day backfill. If an already-visible page crosses the configured time, a page-local timer can ask for the claim; browser suspension requires a fresh check on visible return, not background work. Offline due snapshots continue to work, but offline use has no background sync (`docs/offline-viewing.md:8–21, 31–36`). Use server time and the enrolled device zone to choose the local day; if the zone/claim cannot be confirmed, show no new summary rather than inventing one.
- A **modest extension**—one at-due item schedule—adds item-specific timing, cancellation on item changes, a per-cycle event identity, and recovery/deduplication work. With no phone push it still cannot alert while closed; it can only leave a server-side event for a later visit. A real scheduler/outbox is therefore materially more work for an in-app-only gain. The master plan’s wider S3 stages include durable occurrence/outbox, history/strip and then scheduling/snooze/repeats (`plans/due-date-reminders.md:656–690`); none of that delivery exists in accepted runtime.
- **The summary claim needs durable, idempotent boundaries even without a scheduler.** Suggested key: `(installation, room, device-local date, summary kind/version)`, unique and created/returned transactionally; acknowledge the same stable claim id idempotently. A lost response or second tab should retrieve the same pending claim, not create another. A small tab lease or equivalent can prevent concurrent displays; do not silently turn a failed claim into a second daily prompt. Store the minimum needed for claim/ack/recent status, not a copy of item names; derive content only after current room/device authorization. That limits stale private data and keeps this distinct from a second history system. Define empty-summary behavior explicitly: skip empty prompts, and decide whether an empty check consumes that day’s claim or a later same-day visible check may claim once due facts appear.
- The current accepted S2 system **stores** device/room preferences, private room/list/item rules and item preview; it does not deliver. The `policies.py` module explicitly excludes occurrence generation and transport (lines 1–6); `preview_item` is pure, bounded and not dispatch authorization (`preview.py:117–130, 195–196`; `EffectivePolicy` comment at `policies.py:47–55`). The API contract says delivery is inactive and preview summaries are per-item contributions, not room aggregates or send promises (`docs/api-reminders.md:3–7, 222–257`). Do not implement a daily room summary by misusing `preview_item` as a delivery engine.

## Architecture, Security, and Compatibility

- **Settings gate is materially ambiguous; do not silently choose.** Current due behavior says personal settings are hidden “until phone notifications are ready” (`docs/due-date-reminders.md:57–64`; switch is `false` at `personal-reminders.ts:1`). The accepted S3 brief, although itself only an input to this review, says to restore those entry points for “Durable in-app reminders” and re-enable skipped tests (`plans/batches/reminders-s3.md:28–47`). The master describes an in-app-only S3 with no phone-delivery promise (`plans/due-date-reminders.md:656–690`), but later says settings remain hidden until S3 and puts S3 on hold (`:834–845`). It is unclear whether “phone notifications ready” means OS push only or any in-app reminder. **Recommendation:** keep the current UI hidden pending an explicit owner decision on this narrow in-app-only exception/wording. This scout does not decide it. For a foreground-only summary, do not infer consent from S2’s stored default `daily_summary`, an old enrollment, or an old custom/scheduled policy: delivery was never active. Use a separate explicit opt-in for the new behavior. Preserve old policy rows; make unsupported saved advanced rules visibly paused/unsupported, never execute them or erase them under the reduced release.
- **Device/room isolation is deliberate.** Room authorization is checked on every API route; private policy/preview also requires this device cookie and enrollment, and targets must belong to the authorized room (`src/api/reminders.py:355–390`; `src/api/reminder_policies.py:77–87, 127–142, 255–277`). The device’s settings apply across its enrolled rooms, but room/list/item policies are per installation and room (`docs/api-reminders.md:3–5, 108–132, 134–143`). Share links only grant one-list access, not room authorization. A summary claim must be partitioned by both device and room; never aggregate private names across rooms or devices or write summary data into the shared feed.
- **Preserve revocation.** A grant binds the installation to a room token hash and authorization version; sign-out/token revocation/password change cuts grants, expiry is checked, and only explicit `POST enrollment` resumes (`identity.py:188–211, 227–280`; `docs/api-reminders.md:31–62`). A summary read/claim/ack must revalidate room access and active enrollment, and revoked/stale open UI must not display old private content. Policies/history are retained in storage after revocation; access must remain gated until explicit re-enrollment.
- **Duplicate prevention and safe recovery are new obligations, not provided by S2 write idempotency.** S2 `op_id`/revision rules protect settings writes, not summary displays or scheduled occurrences (`docs/api-reminders.md:182–206`). For the foreground candidate, a unique daily claim plus stable response/ack idempotency and cross-tab race handling are the smallest credible protection. If adding at-due scheduling, event identity should also include the item’s due cycle/rule, with atomic cancellation on completion, date change/delete, and revocation; repeated polling/restarts must not issue duplicate prompts. Fail closed on revoked grant, missing/invalid timezone or unconfirmed timed instant; the preview already returns disabled reasons rather than fallback predictions (`preview.py:129–145`).
- **Architecture wording has a real documentation mismatch.** `ARCHITECTURE.md:59–63` says the device secret is “stored only as a hash in an HTTP-only device cookie,” which reads as if the cookie contains a hash. Actual source issues a random secret, reads and sets that raw secret in an HttpOnly cookie, and hashes it for the SQLite `secret_hash` lookup/storage (`src/api/reminders.py:46–50, 140–149, 301–304`; `src/reminders/identity.py:91–107`; `src/database_setup.py:839–843`). The intended security statement is: **raw random bearer secret in the HttpOnly cookie; only its hash in the database; never in JavaScript, response body or logs.** This is a documentation contradiction, not evidence that the runtime stores the cookie hash. Also retain the one-FastAPI-process/one-SQLite-instance boundary (`ARCHITECTURE.md:14–24`); adding a scheduler would be a larger architecture/runtime concern than the foreground claim endpoint.
