   - Module docstring before: At Gate A the real iPhone showed a toast as tall as the screen; no test had checked the toast size. These checks measure the toasts on a phone screen, also when several are stacked, with a long message, above an open dialog and on a short (landscape) screen.
   - After: At Gate A, the real iPhone showed a toast as tall as the screen. No test had checked its size. These tests measure toast size on a phone with stacked toasts, a long message, an open dialog and a short landscape screen.
   - Reason: split the finding from the test scope and shorten the list without changing the historical finding or coverage.
   - Helper docstring before: Measure the toasts on screen; at least `count` of them. Toasts go after 4 s, so the test waits for a count, not an exact one.
   - After: Check that at least `count` toasts are small and inside the screen. Toasts disappear after 4 s, so the test waits for a count instead of an exact number.
   - Reason: say what the helper checks and express the 4-second timeout behavior plainly. The count and timing remain unchanged. (The backticks here stand for the original Markdown backticks around `count`.)

4. `tests/api_helpers.py`
   - Before: Direct database setup. These replaced `database_crud` helpers that only tests used. Each one calls a live locked helper in one write transaction, or runs the same SQL the live code runs.
   - After: Direct database setup. These helpers replaced `database_crud` helpers that only tests used. Each calls a live locked helper in one write transaction or runs the same SQL as the live code.
   - Reason: make the referent explicit and remove repeated wording. The historical replacement and alternatives are retained.

5. `tests/test_api_basics.py`
   - Before: Every kind of error has a handler that answers JSON under /api and leaves other addresses to FastAPI's defaults.
   - After: Each error type returns JSON under /api; other addresses use FastAPI's default handlers.
   - Reason: shorten the sentence and state the two conditions directly.

6. `tests/test_api_conflicts.py`
   - Before: A "set" op carries the `base_seq` the page saw. When the row changed after that and the stored value differs from what the op wants, the op is rejected with `changed_meanwhile`. Applied answers carry the row's `changed_seq`, so the device can rebase its own queued ops. Two devices are two sequences of ops on one client here: the server only sees the ops and their base seqs.
   - After: A "set" op carries the page's `base_seq`. If the row changed later and its value differs from the requested value, the server rejects the op with `changed_meanwhile`. Applied answers include the row's `changed_seq`, so the device can rebase its queued ops. These tests model two devices as separate sequences of ops sent by one client. The server sees only the ops and their base sequences.
   - Reason: clarify the condition for rejection and describe the test model in shorter sentences. The conflict condition, response code, sequence field, and one-client test model are unchanged.
