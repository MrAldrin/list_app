# Test-suite reduction methods

Research input for lr-4rc. No app source, tests or prior evidence were read. The only app context used is Python + Svelte and a three-engine Playwright suite of about 10 minutes. **Facts** are sourced; **recommendations and gain estimates** are opinions, not measurements of this app. Rank is by likely benefit, not certainty.

1. **Keep broad journeys, move detail down.** Put pure rules in unit tests, request/response contracts in API tests, and component behavior in frontend tests. Keep a few critical end-to-end journeys in the browser. Fact: the [test pyramid](https://martinfowler.com/articles/practical-test-pyramid.html) recommends different test levels and warns that broad tests are costly. Opinion: potentially high gain; medium migration cost. Risk: a lower-level test cannot prove the whole path works.
2. **Reduce the browser matrix for fast feedback.** Run a representative browser for routine feedback; keep critical journeys and browser-sensitive layout, input and storage behavior on Chromium, Firefox and WebKit, and run the full matrix before release. Fact: [Playwright projects](https://playwright.dev/docs/test-projects) support one or multiple browser configurations. Opinion: potentially high feedback gain, but no fixed speedup: setup and parallelism matter. Cost: classify and maintain tests. Risk: a single-engine run misses engine-specific failures; WebKit is not a real Safari device.
3. **Remove or merge with an assertion map.** Require each cleanup proposal to list tests to remove or merge and map every old assertion and distinct input to its retained test, or explain why it is no longer needed. Use a strong model to propose this list and challenge it; a person checks the mapping and runs the retained tests. Facts: [reduction studies](https://digitalcommons.unl.edu/csetechreports/82/) disagree on fault-detection loss; [AI-generated assertions](https://arxiv.org/abs/2501.02901) can be wrong. Opinion: medium potential gain; medium review cost. Risk: matching coverage or assertions alone does not prove equal fault detection, and a model can miss behavioral differences.
4. **Measure before optimizing.** Rank slow setup, test and teardown phases; inspect the largest costs before selecting candidates. Fact: [pytest durations](https://docs.pytest.org/en/stable/how-to/usage.html#profiling-test-execution-duration) reports slow phases. Opinion: indirect but potentially high gain when a few tests dominate; low measurement cost. Risk: one run may mislead, and duration alone does not establish test value.
5. **Select affected tests for quick feedback.** Map changed areas to tests with markers or impact analysis; fall back to a full run for shared or uncertain changes and run the full suite before release. Fact: [Google's test-selection research](https://research.google/pubs/taming-google-scale-continuous-testing/) studies selecting tests to reduce workload. Opinion: medium feedback gain, with ongoing mapping cost; possibly too costly for a small app. Risk: stale or incomplete dependencies miss regressions. Markers select tests; they do not infer impact by themselves.

These are candidates for lr-4rc, not approval to change tests or release checks.
